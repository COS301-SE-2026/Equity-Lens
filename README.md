## Discover EquityLens

EquityLens helps retail investors turn fragmented portfolio statements and market information into clear, actionable understanding. Import investments, explore allocation and performance, follow market-moving news, and ask an AI assistant questions about your portfolio, all from one web application.

## Built for Smarter Investing

| **Understand your portfolio** | **Stay informed** | **Explore with AI** |
|:---|:---|:---|
| Import PDF and Excel investment statements. | Follow portfolio-related and wider market news. | Ask investment questions through a conversational assistant. |
| Review holdings, allocation, indicators and performance. | Investigate news-linked market events. | Discover similar stocks and explore opportunities. |
| Generate a shareable portfolio snapshot. | Connect market movements to financial context. | Receive contextual portfolio insights. |

## Technology & Architecture

**React + Vite** on the frontend, **FastAPI** for the API, and **PostgreSQL** for persistent data - deployed with AWS services and automated through GitHub Actions.

| Area | Technologies |
|:---|:---|
| **User experience** | React 19, Vite 7, Tailwind CSS, Recharts, Framer Motion, React Hook Form |
| **API and processing** | FastAPI, Python 3.11, SQLAlchemy, Alembic, pandas, NumPy |
| **Identity and security** | AWS Cognito, email verification, TOTP MFA |
| **Data and intelligence** | PostgreSQL 16, AWS Bedrock (Claude), yfinance, Alpha Vantage, NewsData |
| **Import and reporting** | pdfjs-dist, SheetJS/xlsx, portfolio snapshot generation |
| **Delivery** | Docker, GitHub Actions, Terraform, Amazon ECR, EC2, AWS RDS |

## Getting Started

### Prerequisites

- Docker Desktop (required)
- Node.js 22+ (Node 22.22.0 is what CI runs against; needed for running frontend tests locally)
- Python 3.11+ (for running backend tests locally)

### Environment Setup

Copy the example env files before first run - Docker Compose will fail to start without `backend/.env`:

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Fill in `AWS_COGNITO_USER_POOL_ID` and `AWS_COGNITO_CLIENT_ID` in the backend env file, and the `VITE_COGNITO_*` variables in the frontend env file, with the team's development Cognito pool values. Set `NEWSDATA_API_KEY` for the News page to return real results.

`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` are also required in `backend/.env`. Both Cognito authentication and the AI assistant (Bedrock) construct their boto3 clients with these credentials explicitly, so login and AI chat will not work without them.

> By default, the backend serves cached/local price data only. Live market data fetches (yfinance) are gated behind `ALLOW_LIVE_MARKET_FALLBACK=true` in `backend/.env`, which is not set in `.env.example`. Add it if you need live prices during local development. `ALPHA_VANTAGE_API_KEY` is optional and only provides live data for non-JSE ticker symbols.

### Running the Project

The entire stack (frontend, backend, database) runs via Docker Compose.

```bash
# Start all services
docker-compose up

# Rebuild after pulling changes
docker-compose down
docker-compose up --build

# Wipes the database
docker-compose down -v
docker-compose up --build
```

Once running:

| Service | URL |
|---|---|
| Frontend | http://localhost:5173 |
| Backend API | http://localhost:8000 |
| API Docs (Swagger) | http://localhost:8000/docs |

## Development and Contribution Guidelines

Contributions follow a pull-request workflow. The conventions below describe the team’s branching and review workflow.

<details>
<summary><strong>Branching strategy and pull request conventions</strong></summary>

### Branch Hierarchy

```
main
└── dev
    └── feature/*, fix/*, docs/*, test/*, refactor/*, chore/*
```

### Rules

- `main` - always deployable and demo-ready. Only merged into from `dev` before each demo.
- `dev` - primary integration branch. All feature branches merge here first.
- Never commit directly to `main` or `dev` - always via a Pull Request.
- All PRs into `dev` require at least two approved reviews and a passing CI pipeline before merging.
- Delete the branch after merging.

### Branch Naming Convention

```
[type]/[description]/[INITIALS]
```

**Examples:**
```
feature/portfolio-csv-import/JH
feature/dashboard-sector-chart/AVS
fix/jwt-token-expiry/AS
docs/srs-functional-requirements/JH
refactor/market-data-caching/AVS
chore/update-dependencies/JKH
```

### Branch Types

| Type | Purpose |
|------|---------|
| `feature` | New functionality |
| `fix` | Bug fix |
| `docs` | Documentation only |
| `test` | Adding or updating tests |
| `refactor` | Code restructure without behaviour change |
| `chore` | Dependencies, config, tooling updates |

### Team Initials

| Member | Initials |
|--------|----------|
| Abdulrahman Sabah | AS |

### PR Naming Convention

```
[INITIALS] : short description of what this PR does
```

**Examples:**
```
JH : feat: add portfolio CSV import endpoint
AS : fix: resolve JWT token expiry bug
AVS : docs: update SRS functional requirements
JKH : chore: update dependencies
```

### PR Rules

- PRs must reference the related GitHub Issue using `Closes #[issue number]` in the description
- At least two team members must review and approve before merging
- CI pipeline must pass before any merge is allowed
- Delete the branch after merging
